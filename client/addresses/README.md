# Client addresses - surviving an official client update

The 2026 client plugins never hardcode an address. They ask `caddr::va(caddr::kName)` (`client/include/client_addrs.h`),
which picks the address for the RUNNING `Fiesta.exe` by its PE TimeDateStamp. On a build the table does not know, every
plugin logs `<plugin>: unknown Fiesta.exe build ... - not hooked` and leaves the client stock.

| file | what |
|---|---|
| `symbols.json` | every address by name: its value in the REFERENCE exe (official US 10.6.4), code / data, which plugin uses it |
| `signatures.json` | generated by `make`: per symbol a masked byte signature (relocated operands and rel32 branches wildcarded) |
| `builds/<stamp>.json` | generated by `resolve`: the addresses in one exe build (10.6.4 = `6AA04F02`, 10.6.6 = `6AB41A55`) |
| `client_sigs.py` | `make` / `resolve <exe>` / `header` |

## After an official update

```
python client_sigs.py resolve "<new client>/Fiesta.exe"   # -> builds/<stamp>.json + a report (old -> new, how found)
python client_sigs.py header                               # -> ../include/client_addrs.h with every known build
..\..\common\build_plugin.bat client <plugin>              # rebuild the plugins (all of them)
```

Read the report: every symbol should say `fwd` / `back` / `call` / `anchor` with a delta close to its neighbours'
(code moves by a few hundred bytes per region, `.data` by whole pages). `NOT FOUND` or a multi-hit means the code around
that address changed: find it by hand (disassemble near `old + typical delta`, compare with the reference), write it into
`builds/<stamp>.json`, rerun `header`. The plugins' own stock-byte checks are the second safety net - a plugin whose site
changed shape refuses to patch even when an address resolved.

## Adding a symbol

Add it to `symbols.json` with its reference-exe address, rerun `make`, then `resolve` every build in `builds/` (their
exes) and `header`. A plugin then uses `caddr::va(caddr::kName)` and lists it in its `caddr::missing({...})` guard.
Stock-byte checks must not contain absolute addresses or rel32 displacements - compare those against resolved
addresses instead (see `exit_scene_order`, `mastery_top_tier`, `minimon_pickup_keep`, `map_mark_dedupe`).

## How the methods work

- **fwd**: signature starting at the address, grown until unique in the reference exe (+8 bytes margin).
- **back**: signature ending at the address - when the code at the address changed but the code before it did not.
- **call**: for a function whose start is a generic SEH prologue: a unique call site to it; resolve follows its rel32.
- **anchor** (data): an instruction that holds the address as an operand (from the reference exe's `.reloc` table);
  resolve finds the instruction and reads the operand.

The 2016 client's PDB (`Z:/ClientSource/Fiesta.pdb`) is where most of these functions were first identified by name;
the names in `symbols.json` keep that link. The signatures only bridge 2026 builds to each other.
